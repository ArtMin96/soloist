## Register

product

## Users

Developers and AI-tooling power users on Linux who run a **local dev stack** (servers, workers, build
watchers) alongside **one or more CLI coding agents** (Claude Code, Codex, Gemini, Aider, OpenCode,
Goose, Amp…) at the same time.

- **Context of use:** a long-running supervisor that may stay open for **hours or days** on a Linux
  desktop. The user is constantly context-switching — watching a server's logs, answering an agent's
  permission prompt, restarting a crashed worker, orchestrating several agents at once. Often the
  window is glanced at, not stared at: it must communicate state at a glance and pull attention only
  when something actually needs them.
- **Job to be done:** keep the whole stack alive and observable from **one place**; drop into any
  process's terminal and interact with it; coordinate multiple agents (todos, locks, scratchpads,
  fire-when-idle timers) **without babysitting** — all driven by a committable `solo.yml`.
- **Expertise:** high. These are terminal-native engineers who value speed, keyboard control, and
  honesty over hand-holding or marketing.

## Product Purpose

Soloist is a **native Linux process-supervisor + AI-agent-coordination workspace** — a "metaharness." It
runs your dev stack and coding agents as managed processes, keeps them alive (auto-restart, file-watch
restart, rate-limited), and surfaces status / logs / ports / idle-state at a glance. On top of
supervision it exposes a shared, **project-scoped coordination surface** (todos, scratchpads, locks,
timers, key-value) over **MCP**, so a lead agent can orchestrate worker agents token-free.

It is **not** a coding agent, **not** a terminal emulator, **not** a worktree orchestrator — it runs the
agent CLIs the user already has and layers coordination on top.

**Appearance is content, not a display preference.** How Soloist looks is a small library the user
owns. Built-in themes ship with the app; any of them can be duplicated, edited live, copied to the
clipboard, exported as a single JSON file, and imported back. A theme is a **portable artifact** — the
kind of thing a developer commits to a dotfile repo, hands to a teammate, or brings over from the
editor and terminal they already themed. The format is deliberately not private to us: Soloist reads
and writes T3-compatible v1 theme JSON, so a palette can travel. What Soloist owns is not the pigment
but the *contract*: it consumes whatever palette it is handed, names every place a color can land, and
stays legible — including inside the terminal, whose 16 ANSI slots follow the theme like everything
else.

**What success looks like:** a developer writes a `solo.yml`, launches Soloist, trusts the commands, and
starts a multi-process stack (including a real agent) with **one action** — then lets it run reliably
for days. Crashes self-heal and notify; agents coordinate through the shared workspace; and the
dashboard makes the live state of *many* processes instantly legible without the user hunting for it.

## Brand Personality

**Quiet · precise · fast · trustworthy.**

- **Voice/tone:** confident, technical, unfussy. Plain language, no marketing gloss, no exclamation
  marks. It speaks to experts as experts.
- **Quiet:** the interface recedes by default and speaks only when there is something to say — a
  crash, an agent waiting on you, a worker going idle. Silence is the resting state, not a UI that
  has nothing to show.
- **Precise:** every reading is honest and immediate. A number, a status word, or a glyph on screen is
  never approximate, never decorative, and never lags the real `ProcStatus`/`AgentActivity` state
  machines.
- **Fast:** the app is native and responsive under a dozen chatty processes at once — instant status
  flips, no animated list churn, no UI that waits on the network to feel alive.
- **Trustworthy:** it wears a **native Linux desktop shell** — a unified toolbar, a source-list
  sidebar, hairline structure, outlined controls, glass only where something genuinely floats — and
  earns confidence by being unremarkable in the way a well-built native tool is, kept open for days
  without ever feeling like a web page wearing a window frame. Two pragmatic departures keep it honest
  on Ubuntu: **the window is opaque** (no desktop vibrancy, nothing showing through from behind the
  app) and **window controls stay top-right** (restyled), where a Linux/GNOME user expects them, not
  faked traffic lights. Glass is a material Soloist uses *inside* its own window, on the surfaces that
  genuinely float above the work; it is never the window itself. `DESIGN.md` §3 draws that line
  precisely, with numeric budgets.

## Anti-references

What Soloist must **not** look like — the generic-AI-UI failure modes, named explicitly so they are
falsifiable in review, not a vibe:

- **Gradient text and glowing cards** — `background-clip: text` gradients, cards with a soft outer
  glow standing in for hierarchy. Structure is hairlines and tonal layering, not glow (`DESIGN.md`
  §3, §12).
- **Card-in-card nesting** — a card inside another card's padding, each with its own border and
  shadow. Hierarchy stays flat: one surface, then content (`DESIGN.md` §12).
- **Eyebrow labels** — tiny tracked-UPPERCASE section headers ("O V E R V I E W"). Group headers are
  small sentence-case labels (`DESIGN.md` R4.5).
- **Side stripes** — a colored `border-left`/`border-right` used as a status or selection marker.
  Selection is an inset azure fill, transitioning in place (`DESIGN.md` R7.9, R12).
- **Decorative blur** — a frosted panel, hero section, or card grid that floats nothing and reports
  nothing. Glass in this app means "temporarily above the work" or "this control is engaged," never
  ambience (`DESIGN.md` §3, R3.19).
- **Icon soup** — icons stacked for visual interest rather than distinct meaning (`DESIGN.md` R6.6).
- **Everything-is-a-badge** — pills and chips used for information that should be plain text or a
  status dot; a badge that carries no state is decoration wearing a shape.
- **Tinted group backgrounds** — a colored wash used purely to group related content where a hairline
  divider would do (`DESIGN.md` R3.1–R3.2).
- **The generic SaaS dashboard** — gradient hero-metric cards, identical icon+heading card grids,
  purple gradients, the analytics-template look.
- **The cream/beige "AI default"** — warm paper/sand/parchment background, tiny tracked-uppercase
  eyebrows, `01 / 02 / 03` numbered section scaffolding. These are the saturated AI-generation tells.
- **A web-app-in-a-window** — heavy browser chrome, Electron-y bloat, anything that reads as
  "obviously a website" rather than a native desktop app.
- **Toy / skeuomorphic** — oversized radii, heavy drop shadows, playful mascot/clip-art energy. This
  is a serious tool for serious work.

## Design Principles

Each maps to the section of `DESIGN.md` that turns it into testable rules.

1. **Structure over decoration.** Depth, grouping, and hierarchy come from hairlines and tonal
   layering, never from a card, a gradient, or a shadow on a surface at rest. → `DESIGN.md` §3.
2. **Signal over chrome; one accent, spent on meaning.** Saturated color reports a process's, an
   agent's, or the repository's state; azure marks focus/selection/the one primary action and nothing
   else. Decoration that carries no information is debt. → `DESIGN.md` §2.
3. **Read like the desktop it runs on.** Type and icons resolve to what Ubuntu actually ships, not a
   platform this app is only borrowing a feel from. → `DESIGN.md` §4, §6.
4. **Density with rhythm.** Show a lot — process tree, terminals, status, metrics — without clutter,
   earned through hierarchy, spacing, and a compact type scale, never cards-everywhere. → `DESIGN.md`
   §5.
5. **Earned familiarity; every control tells the truth about its own state.** A control behaves like
   its native-desktop equivalent, with the complete state set defined — default, hover, focus,
   active, selected, disabled, loading, error — never inferred from opacity alone. → `DESIGN.md` §7.
6. **Motion confirms, it never decorates.** A state change is answered by native spring physics, felt
   once and never waited on, always reduced-motion-safe; never a default cross-fade with nothing to
   report. → `DESIGN.md` §8.
7. **Keyboard-first, expert-respecting, and honestly announced.** Every primary action is reachable by
   keyboard; status that changes on screen is also announced to a screen reader, not only shown. →
   `DESIGN.md` §9.
8. **Native and invisible, down to the window itself.** The titlebar, controls, and window behavior
   feel like a first-class Linux desktop citizen, not a borrowed shell. → `DESIGN.md` §10.
9. **The palette belongs to the user.** Soloist ships a default look and defends legibility on any
   palette; it authors no color of its own outside theme data, so a hard-coded color is always a bug
   waiting for the next theme switch to expose it. → `DESIGN.md` §2 (Theme System).

## Accessibility & Inclusion

- **Contrast:** target **WCAG 2.2 AA** — body text ≥4.5:1, non-text UI ≥3:1 — on **every** palette,
  not only the ones shipped. Colors the app derives are corrected to clear the floor mechanically;
  colors a user-authored palette supplies are reported, not silently overridden. Neither half may be
  described as the guarantee the other provides (`DESIGN.md` §2, §9).
- **Theme:** a **library**, not a switch — built-in themes plus anything the user authors or imports,
  light and dark halves selected **independently**, `system` following the OS by default. A theme may
  publish only one appearance; a selection fails honestly rather than silently substituting.
- **Motion:** every animation has a `prefers-reduced-motion: reduce` fallback that removes it or makes
  it instant (`DESIGN.md` R8.7).
- **Transparency:** every translucent surface has a `prefers-reduced-transparency: reduce` fallback
  that resolves to an opaque equivalent. Glass is an enhancement, never the thing carrying meaning
  (`DESIGN.md` R3.17).
- **Keyboard:** full keyboard operability with a visible, `:focus-visible`-gated focus ring is a
  product floor (Principle 7), not an a11y nicety (`DESIGN.md` §9).
- **Screen readers:** Orca on Linux/WebKitGTK is the deployment reality. Status changes that are shown
  visually must also be announced via ARIA live regions — this is a known current gap, tracked in
  `DESIGN.md` §13, not yet a met bar.
- **Color-blind-safe status encoding:** the UI leans on status dots (running/crashed/idle/working/
  error); every status is glyph + color + label, never hue alone (`DESIGN.md` R2.6, R9.2).
